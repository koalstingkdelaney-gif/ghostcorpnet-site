    Why an exit plan belongs in the governance file before you need it

    Production AI agents are now a core operational dependency. In 2025, 62 percent of organizations were experimenting with AI agents and 23 percent were scaling agentic systems in at least one business function (BudEcosystem 2025). When a vendor raises prices, degrades service, or shuts down, the cost of improvisation is measured in lost audit trails, broken tool grants, and stalled releases. An exit plan written today becomes a control document that auditors, security reviewers, and future platform teams can reference without reverse‑engineering a live system.

    A developer documented an agent burning over 700 dollars in API costs in 72 hours from an infinite loop with no budget controls (Reddit r/IndieDev 2025).

    Exit inventory – what you must catalog

    Prompts and system instructions

    Export every system prompt, user‑level prompt template, and version‑controlled instruction set. Store them in a repository‑agnostic format (plain text or JSON) with a hash for integrity verification.

    Tool grants and credentials

    List each external tool the agent may call: API keys, OAuth tokens, service‑account emails, and the exact scopes granted. Record the credential rotation schedule and the owner responsible for revocation.

    Data and conversation history

    Identify the storage location, retention policy, and export format for all conversation logs, user‑generated content, and any derived embeddings. Note whether the vendor stores data in a proprietary blob or a standard format such as Parquet or CSV.

    Audit trail and logs

    Capture the schema of the vendor’s audit log (timestamp, actor, action, outcome). Verify that the log includes model‑level decisions, tool invocations, and error codes. Export a sample set to confirm completeness.

    Evals and test sets

    Collect the evaluation harness: golden‑set prompts, expected outputs, metric definitions (accuracy, latency, cost), and the CI/CD pipeline that runs them. Version these artifacts alongside the agent code.

    Contracts and billing

    Attach the master services agreement, any addenda, the current pricing schedule, and the most recent invoice. Highlight renewal dates, price‑change notice periods, and termination clauses.

    Portability traps that stall migrations

    Proprietary prompt formats

    Some vendors wrap prompts in a binary envelope or add vendor‑specific control tokens. Without a documented schema, you cannot replay the exact prompt on another runtime.

    Vendor‑locked tool schemas

    Tool definitions may reference internal function IDs or custom parameter validation that only the vendor’s gateway understands. Map each tool to an open specification (OpenAPI, JSON‑Schema) before you depend on it.

    Model‑specific behavior

    Agents tuned to a particular model’s token‑level quirks (e.g., stop‑sequence handling, function‑call format) will behave differently on a new model. Document the behavior assumptions and create regression tests for each.

    Data export limits and retention windows

    Vendors often cap bulk exports to [DAYS] days of history or require a manual request that takes [DAYS] business days. Build an automated export job that runs on a schedule and stores the output in your own object store.

    Phased migration timeline

    Phase 1 – Prepare (Weeks 1–[WEEKS])

    1. Complete the exit inventory sheet.
    2. Negotiate export‑format and timeline clauses if not already in contract.
    3. Build an export test script that pulls a full snapshot of prompts, tool grants, logs, and eval data into your staging bucket.
    4. Validate the export test against a checksum list; record results in the migration tracker.

    Phase 2 – Parallel run (Weeks [WEEKS]–[WEEKS])

    1. Deploy a shadow instance of the agent on the target platform using the exported artifacts.
    2. Run the full eval suite against both the legacy and shadow agents; log discrepancies.
    3. Execute a parallel‑run checklist: traffic mirroring percentage, latency budget, cost ceiling, audit‑log parity.
    4. Obtain sign‑off from security, compliance, and product owners before increasing traffic share.

    Phase 3 – Cut over (Day [DATE])

    1. Switch DNS / routing to the new endpoint for 100 % of production traffic.
    2. Monitor the real‑time dashboard for error‑rate spikes, cost anomalies, and audit‑log gaps for at least [DAYS] hours.
    3. If any critical metric exceeds its threshold, roll back using the documented rollback runbook.

    Phase 4 – Decommission (Weeks [WEEKS]–[WEEKS])

    1. Confirm that all conversation history required for compliance has been archived in your own store.
    2. Revoke all vendor‑issued credentials and delete any remaining data per the data‑deletion attestation clause.
    3. Complete the decommission sign‑off document; archive it with the exit inventory sheet.

    Contract clauses to negotiate up front

    • Export format clause – Vendor must provide prompts, tool schemas, logs, and eval data in an open, documented format (JSON, Parquet, CSV) within [DAYS] calendar days of request.
    • Export timeline clause – Define a maximum lead time for bulk exports (e.g., 5 business days) and a penalty for missed deadlines.
    • Data deletion attestation – Vendor supplies a signed attestation that all customer data has been purged from their systems within [DAYS] days of termination.
    • Transition assistance – Vendor allocates engineering hours (minimum [DAYS] hours) to help map proprietary formats to open specs during the parallel‑run phase.
    • Price‑change notice – Minimum [DAYS] days written notice before any price increase, with a cap on the percentage increase per renewal cycle.

    Common mistakes that derail exits

    • Treating the exit plan as a one‑time document instead of a living artifact updated each sprint.
    • Assuming the vendor’s “export” button yields a complete, queryable dataset; always run an export test.
    • Neglecting to version‑control eval test sets; drifting benchmarks make parallel‑run comparison meaningless.
    • Overlooking credential rotation – stale API keys become a security liability after cut‑over.
    • Failing to capture the audit‑log schema; without it you cannot prove compliance on the new platform.
    • Skipping the dry‑run; a tabletop exercise does not surface latency or cost surprises.

    Running the first dry run this quarter

    Schedule a two‑day window before the next renewal date. Execute the export test, spin up the shadow agent, and run the full parallel‑run checklist. Record every deviation in the migration tracker and update the exit inventory sheet accordingly. The goal is not a flawless migration but a documented baseline that tells you exactly how many [DAYS] of engineering effort a real cut‑over will require. Gartner forecasts 40 percent of enterprise applications will incorporate task‑specific AI agents by 2026, up from under 5 percent in 2025, so the discipline you build now compounds across every future agent you operate.

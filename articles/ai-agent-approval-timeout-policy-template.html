AI Agent Approval Timeout Policy Template: What Happens When No Human Answers

    Every approval gate eventually meets the same moment: an agent has asked, and no human answers. The approver is in a meeting, on leave, or looking at a queue that scrolled past. What the system does in that silence is the real policy — not the gate you designed, but the timeout behind it. This AI agent approval timeout policy template makes that moment explicit: how long a request may wait, who gets reminded, who it escalates to, and what happens when the clock runs out.

    An approval timeout is the maximum time an AI agent waits for a human to decide a gated action — a bound, like a plan's other bounds: workload, data class, resources, time, location, egress, storage, cost, and expiry. The request is created with its expiry visible to the approver, and when it passes without a decision, the request ends in a defined state. The alternatives are both bad: no expiry, and the request dangles until someone treats age as settlement; auto-approval on expiry, and silence opens the gate. The Governed Agent Mesh Playbook is fail-closed — missing approval means no external action, and the block is recorded exactly.

    Why silence is not consent¶

    Silence is not consent, for three practical reasons. First, a missing answer usually means a missing human, not a considered yes: the notification failed, the approver is away, or the queue is buried. Second, gated actions are gated because their consequences are hard to reverse — money, contracts, external outreach, credentials, and permission changes do not become safer because nobody replied. Third, an audit trail that reads "no answer, so it ran" cannot be defended later: treating the absence of the control as the control removes it while keeping its paperwork.

    Auto-approving on timeout is the worst version of this: no named human decided, so none can be asked why the action ran, and the busier the approver, the wider the gate opens. A timeout therefore ends in one of three recorded outcomes, and auto-approval is not among them:

    • Escalate — hand the pending request to a named backup approver before expiry, while a decision is still possible.
    • Block — at expiry the action does not happen, and the block persists as an exact blocked result.
    • Expire silently — only for draft-only work that never executes and never contacts anyone; nothing was going to run.

    Set the timeout by risk tier¶

    One timeout for every request is the first design error: the expiry follows the tier, because the cost of a wrong "yes" and the cost of a stalled "wait" differ by tier. Each window's length is a policy value — [TIMEOUT] per tier — set from how your approvers actually work, not copied from another team: a window nobody can answer inside manufactures blocks, and an endless one leaves actions dangling. The clock starts at submission, and the expiry, reminder point, and consequence of silence are visible inside the request.

    • Hard-gated — money, contracts, external outreach, credentials, permission changes, and legal actions. The timeout never expires into approval, at any length. At expiry the request blocks, and the action does not happen until a human decides on a fresh request.
    • Bounded-auto — routine work inside an approved, bounded plan runs without asking. What times out here is a request to step outside the bound — a larger workload, a new data class, a higher spend ceiling. It expires into a block: the plan keeps its original bounds.
    • Draft-only — preparing proposals, composing messages, and planning. A draft request may expire silently: a draft nobody approved was never going to be sent or executed, so the expiry just closes the file.

    What the template must record¶

    A timeout can only be enforced, escalated, and later proved if the request carries the right fields from creation. Copy these into your policy template:

    • Request ID — unique to this request, including against earlier requests for the same action.
    • Agent identity — the stable, owner-scoped identity of the agent asking; anonymous or shared actors are rejected, not timed out.
    • Action and target — the exact action and the exact thing it acts on, plainly enough that the approver decides on the real action, not a summary.
    • Risk tier — hard-gated, bounded-auto, or draft-only; the tier decides which timeout behaviour applies.
    • Bounds — the workload, data class, resources, time, location, egress, storage, and cost bounds the approved action would run inside.
    • Expiry — when the timeout fires, set at creation and visible in the request itself.
    • Primary and backup approver — two named humans, never a team alias; the backup is named at creation, not improvised after the primary goes silent.
    • Fallback — the recorded outcome at expiry for this tier: escalate, block, or expire silently.

    Underneath sits the audit discipline: every request, reminder, escalation, approval, rejection, and block writes a row — actor, action, target, outcome, timestamp — hash-linked to the row before it, so the sequence can be checked rather than trusted.

    The escalation ladder¶

    Escalation is not a second chance for the agent; it is a route for the decision to reach a human who can still make it in time, climbed by the clock, not by the agent asking louder. First, one reminder to the primary approver at the policy's reminder point, restating the action, target, and expiry so they can decide from the reminder itself. Second, if the primary has not decided, the request escalates to the named backup approver with the full request and its remaining time. Third, at expiry, the request blocks and the block is recorded. There is no fourth rung: a request two named humans did not answer is a request the organisation did not approve.

    What the agent may and may not do while waiting¶

    While a request is pending, and after it has blocked, the agent must not:

    • Re-run the gated action — not in whole, in part, or "just the harmless bit" while the decision is open.
    • Split the action — pieces of one gated action are gated together under the original request, however small each piece looks.
    • Route around the gate — reaching the same outcome through a different tool or agent is a bypass, and the attempt itself is recorded.
    • Refresh its own expiry — the requester cannot extend or restart the clock that is judging its request.
    • Resubmit in a loop — automatic resubmission turns one unanswered question into queue spam until a tired human clicks yes.

    The agent may continue other, already-bounded work that does not depend on the pending decision, recording that it is doing so.

    A worked example: an outreach request nobody answered¶

    A hypothetical walkthrough. An agent prepares an external outreach message — drafting is draft-only, but sending external outreach is hard-gated, so the send waits for a named approver. The request carries every field from the template above, with an expiry of [TIMEOUT] for the hard-gated tier.

    At the reminder point the primary has not answered, and the one reminder goes out. Still no decision, so the request escalates to the backup with its remaining time; the backup does not answer either. At expiry the request blocks: the message is not sent, no part of it is sent, and the agent does not re-ask through another tool. The audit trail gains the full sequence — request, reminder, escalation, exact blocked result — and the block surfaces to the owner with the evidence that would unblock it: a human decision on a fresh request. A resubmission, if a human still wants the send, is that fresh request — a new request ID, a fresh review of whether the action is still needed and correctly bounded, and a link back to the blocked original. The agent never resubmits on its own.

    Run this checklist before the first gated request goes live under the policy:

    • Every gated action class has a tier, and every tier has a written [TIMEOUT], a reminder point, and a recorded outcome at expiry — and no tier expires into approval.
    • Every request carries the request ID, agent identity, action, target, tier, bounds, expiry, and both approvers' names.
    • The escalation ladder is tested with a real request, and the backup approver confirms the escalation actually reaches them.
    • The waiting-period prohibitions are enforced in the runtime, not just written in the policy.

    Common mistakes to avoid¶

    • Treating silence as consent — the failure the whole policy exists to prevent; a timeout that approves is a gate that opens for absence.
    • One timeout for all tiers — a window sized for drafts will stall hard-gated work or rush it; the expiry follows the tier.
    • Escalating to an alias — a backup who is a mailbox nobody reads is a block with extra steps; name a human and test the route.
    • Letting the agent manage its own clock — an expiry the requester can extend is not an expiry.
    • Losing the block — if the timed-out request vanishes instead of persisting as a blocked result, no reviewer can tell a gate that held from a gate that was never asked.

    Conclusion¶

    An AI agent approval timeout policy template decides what your system does when a consequential question gets no human answer. Set the expiry by risk tier, remind once, escalate to a named backup, and at expiry let the gate hold: blocked, recorded, and reversible only by a fresh human decision on a fresh request. A block that is written down is not a failure of the system. It is the system working, in writing.

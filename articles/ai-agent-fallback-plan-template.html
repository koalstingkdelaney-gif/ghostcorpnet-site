AI Agent Fallback Plan Template: Decide in Advance What Your Agent Does When Something Fails

    Most agent failures are not exotic: a model endpoint slows down, a tool returns malformed output, an approval never arrives, a budget runs out mid-plan. What turns them into incidents is the gap between the failure and the decision — nobody decided in advance what the agent should do next, so the agent, or an on-call human at the worst possible moment, improvises. This AI agent fallback plan template closes that gap. Taken from the Governed Agent Mesh Playbook's fail-closed runtime layer, it pre-decides, for every failure class, a bounded degraded mode, the evidence that ends it, and the audit row that proves both happened.

    Why improvisation is the failure¶

    An agent that meets a failure with no plan defaults to one of three bad behaviours. It retries — and a retry against a dead tool or an exhausted budget is the same spend asked again until it slips through or the bill arrives. It degrades silently, answering from stale context or skipping the check it could not complete, so the output looks normal while the guarantee behind it is gone. Or it escalates its own authority, reaching for a different tool or a broader permission to route around the block.

    The Playbook's rule is the opposite: when evidence is missing, the system blocks and records — it never degrades to a warning. A fallback plan extends that rule from single actions to whole failure states: the degraded behaviour is chosen, bounded, and recorded in advance.

    Fallback plan, kill switch, rollback, incident response: four different tools¶

    These four get confused because they all appear in the same bad week:

    • Fallback plan — the pre-written degraded mode entered when a defined failure occurs, so useful work continues inside tighter bounds. This article is about this one.
    • Kill switch — the emergency stop. Necessary, but binary: it ends the work instead of governing it.
    • Rollback — returning a deployment, plan, or grant set to a known-good state. It fixes a bad change, not a live dependency outage.
    • Incident response — the human-led process after harm or suspected harm. A fallback plan shrinks incidents and feeds them evidence; it never replaces the response.

    If your only failure tool is the kill switch, every failure is an outage.

    The five failure classes to plan for¶

    Write one entry per class; a class with no entry will be improvised.

    • Model unavailable or degraded — the endpoint is down, throttled, or returning output you would not ship.
    • Tool or API failure — a required tool errors, times out, or disappears. Dependent actions cannot be half-executed: a plan that needed the tool's result does not get to guess it.
    • Missing approval or evidence — a hard-gated action (money, contracts, outreach, credentials, permission changes) has no recorded human decision. Silence is not approval; the action waits or blocks.
    • Budget or rate limit exhausted — the plan's ceiling is hit. As the Playbook puts it for spend: blocked, recorded as blocked — not retried, not warned, not billed. The stakes are documented: a developer reported an agent in an infinite loop burning over $700 in API credits in 72 hours because nothing in the stack had budget controls or a watchdog.
    • Untrusted or malformed tool output — the tool answered, but its output fails validation. Treating it as real is how a small data problem becomes an external side effect.

    The degraded-mode menu: six ways to do less, safely¶

    A fallback entry names one mode per failure class — every mode a reduction in authority, never an expansion:

    • Read-only mode — look, summarise, and report; change nothing, contact no one.
    • Draft-only mode — prepare proposals, messages, and plans, all recorded and none executed: work product survives, side effects do not.
    • Queue-and-hold — requests are recorded and held unexecuted until the failure clears and bounds are re-checked. A queued request is not a promise to execute.
    • Cached approved answers only — serve responses a human already approved; decline or queue anything new.
    • Human handoff — package the failure, the evidence, and the blocked items into a record for a named human to decide.
    • Full stop — the kill-switch state, for failures where even read-only behaviour cannot be trusted, such as suspected compromise of the agent's inputs.

    The AI agent fallback plan template: fields to copy¶

    One entry per failure class, per agent. Replace every [BRACKET]:

    • Agent identity — the stable, owner-scoped identity this entry governs.
    • Failure class and trigger — one of the five classes, plus the observable signal that declares it: [SIGNAL — e.g. health check, missing approval record, ceiling reached, validation failure].
    • Degraded mode — exactly one: [READ-ONLY / DRAFT-ONLY / QUEUE-AND-HOLD / CACHED-ONLY / HANDOFF / FULL STOP].
    • Bounds inside the mode — workload, data class, resources, time, egress, storage, cost ceiling, and expiry, restated for the degraded state. A mode with no time bound is a new normal, not a fallback.
    • What stays hard-gated — money, contracts, outreach, credentials, and permission changes stay human-decided in every mode.
    • Evidence that ends the fallback — the exact record proving the failure is over: [EVIDENCE — e.g. a successful health check, the recorded approval, the renewed plan]. Modes end on evidence, not timers.
    • Re-entry checks — what is re-verified before normal operation resumes, including re-checking every queued item against its bounds and approvals as they stand now.
    • Owner of the entry — the named human who approved this fallback and who alone may widen it.

    What the agent must never do in fallback mode¶

    Close these routes in the plan itself:

    • Widen its own permissions — a degraded state holds less authority than normal, never more; grant changes are hard-gated human decisions.
    • Switch tools or models to route around a block — an unapproved substitute is an unreviewed dependency adopted mid-incident.
    • Execute the queue blindly on recovery — held work is re-checked against current bounds, approvals, and evidence first; some of it should expire in the queue, and the plan says how long it may wait.
    • Retry without a bound — retries carry a count and a clock from the entry; an unbounded retry loop is the failure wearing a costume.
    • Hide the state — operators must be able to see that the agent is degraded, and why. An unobservable fallback is silent degradation with paperwork.

    Every fallback entry and exit writes an audit row¶

    The Playbook's audit row records actor, action, target, outcome, and timestamp, hash-chained to the previous row so tampering breaks the chain visibly. Fallback adds three rows: entering the mode (with the trigger signal as evidence), every blocked or held action attempted inside it — a blocked action must persist an exact blocked result, because "it probably didn't run" is not an audit trail — and exiting, pointing at the evidence that ended it. Those rows are how you later prove the agent did less, on purpose, for a reason.

    Drill the plan before production does¶

    A fallback plan that has never fired is a hypothesis. Drill each class: take the tool away in staging and watch the agent enter the right mode; let an approval expire and confirm the action blocks; drive a test plan into its ceiling and confirm the block is recorded and the queue does not execute itself on recovery. Then read the audit rows cold — they must tell the whole story without you in the room. Whatever the drill shows the agent improvising is the next line you write into the template.

    Common mistakes to avoid¶

    • One generic fallback for everything — one mode stretched across all five classes governs none of them.
    • Fallback as a warning banner — warning the user while the agent proceeds at full authority is observability, not governance.
    • No exit evidence — modes that end on a timer strand the agent in degraded operation, or snap it back before recovery is real.
    • Unbounded queues — held work with no expiry becomes a backlog of stale approvals waiting to fire in a changed world.
    • A plan nobody owns — if no named human approved the entry, nobody can widen it safely or will maintain it.

    Pre-launch checklist¶

    • Every agent carries one fallback entry per failure class, each naming exactly one degraded mode.
    • Every mode is bounded — workload, data class, time, cost, and expiry restated — and hard-gated actions stay hard-gated in all modes.
    • Every entry names the evidence that ends it and the re-entry checks, including re-checking queued work before it may run.
    • Entry, in-mode blocks, and exit each write hash-linked audit rows; every class has been drilled and read back from the log.

    Conclusion¶

    An AI agent fallback plan template does its work before it is needed: one entry per failure class, one bounded degraded mode per entry, named evidence to end it, an audit row for every transition. Fail closed, do less on purpose, let the record show it.

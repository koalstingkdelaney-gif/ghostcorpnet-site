AI Agent Governance RACI Template: Who Owns, Approves, and Stops Each Agent Action

On this page

    Every governed agent eventually produces a moment that needs one name. An approval queue is waiting and nobody is sure whose decision it is. A plan is burning spend and nobody is sure who may stop it. A block was routed to a team alias that nobody reads. Teams answer these moments with "the team owns the agent" — and that answer is exactly the failure. A team cannot approve, cannot be paged, and cannot sign an audit row. This AI agent governance RACI template replaces the team with four named roles for every decision: who does the work, who decides, who must be asked first, and who only needs to know.

    Why "the team" is not an owner¶

    In the Governed Agent Mesh Playbook, every agent holds a stable, owner-scoped identity — agent:[OWNER]/[NAME] — recorded in an identity registry with its owner, date issued, and status. Grants are issued by a named human, blocks surface to a named human, and hard-gated actions wait for a named human holding the approver role. The routing only works if each decision has exactly one accountable name behind it.

    The stakes are not abstract. Gartner projects that 40% of enterprise applications will incorporate task-specific AI agents by 2026, up from under 5% in 2025 — more agents, more decisions to route. And the cost of a decision with no owner is documented: a practitioner report describes a runaway agent loop that burned over $700 in 72 hours with no budget control in place. A loop like that does not need a committee. It needs one person named, in advance, as accountable for stopping it.

    What RACI means when the actor is an agent¶

    RACI is four letters, and each one maps cleanly onto agent governance:

    • Responsible — the human who prepares and submits the decision: drafts the plan bound, requests the grant, composes the action. The agent is never Responsible; it executes inside bounds a human set.
    • Accountable — the one human who decides. Exactly one per row, never two, and never the agent. If a row has two Accountables, it has none: each can assume the other decided.
    • Consulted — the humans whose input is required before the decision: security on a new tool, finance on a ceiling, the data owner on a new data class. A two-way conversation held *before* the decision, not a notification after it.
    • Informed — the humans who receive the record after the decision: the audit row, with actor, action, target, and outcome. A one-way record, not a discussion.

    Two Playbook rules bind the chart. First, the approver for a hard-gated action must be a human holding the approver role, and the requester is not their own approver — a grant change or ceiling raise approved by the person who asked for it is a control that exists only on paper. Second, every decision writes an audit row — request, approval, block, and outcome alike, hash-linked to the row before it — so the RACI can be checked against what actually happened.

    The template: twelve decision rows¶

    Copy these rows into your wiki or repo and replace every role with a named human. The roles are the starting point; the names make it real.

    • Register a new agent identity. Responsible: the person standing the agent up. Accountable: the Agent Owner who will answer for it. Consulted: Security Reviewer. Informed: Incident Lead.
    • Approve a plan bound (scope, tools, data class, egress, spend ceiling, expiry). Responsible: Agent Owner. Accountable: Approver. Consulted: Security Reviewer, Finance Owner. Informed: Incident Lead.
    • Issue or change a grant. Responsible: Agent Owner, who requests it. Accountable: Approver — changing a grant is a hard-gated action. Consulted: Security Reviewer. Informed: Incident Lead.
    • Open a new data class to an agent. Responsible: Agent Owner. Accountable: Approver. Consulted: Data Owner, Security Reviewer. Informed: Incident Lead.
    • Raise a spend ceiling. Responsible: Agent Owner. Accountable: Approver. Consulted: Finance Owner. Informed: Incident Lead.
    • Approve a hard-gated action (moving money, accepting terms, sending external outreach, reading credentials, changing permissions, legal actions). Responsible: the requester. Accountable: the Approver for that action class. Consulted: the owner of the affected system or budget. Informed: Incident Lead.
    • Grant a policy exception. Responsible: Agent Owner. Accountable: Approver. Consulted: Security Reviewer. Informed: everyone Informed on the original decision — an exception with an expiry, never a silent waiver.
    • Change the model, prompt, or tool set. Responsible: Agent Owner. Accountable: Approver. Consulted: Security Reviewer. Informed: Incident Lead, operators.
    • Promote a version to production. Responsible: Agent Owner. Accountable: Approver. Consulted: Security Reviewer, Finance Owner. Informed: operators, Incident Lead.
    • Declare an incident and use the kill switch. Responsible: whoever detects it — stop first, file second. Accountable: Incident Lead. Consulted: Agent Owner, Security Reviewer. Informed: Approver, Finance Owner.
    • Review the audit trail. Responsible: the reviewer. Accountable: Agent Owner, who answers for the findings. Consulted: Security Reviewer. Informed: Approver.
    • Decommission an agent. Responsible: Agent Owner. Accountable: Approver, who confirms grants are revoked and the identity retired, not just stopped. Consulted: Security Reviewer, Finance Owner. Informed: Incident Lead.

    Filling it in when one person wears several hats¶

    Small teams cannot staff twelve rows with twelve people, and they do not need to. One human may hold the Agent Owner and Finance Owner roles, or be both Responsible and Informed on a row. Two separations survive every team size. The Accountable on a hard-gated row is not the person who requested it — if the owner needs a ceiling raise, someone else holding the approver role signs it, even if that is the only other person on the team. And the agent is never in any column: it can be the actor in an audit row, but accountability is a human property, because only a human can be asked why they decided.

    Where one person genuinely is the whole team, write that down too: a row that honestly names the same human twice, risk noted, is a governed risk — a row that pretends a separation exists is a fiction.

    A worked example: adding a payment capability¶

    A hypothetical walkthrough, using the tier worksheet's own example row. A team wants its operations agent to send a payment. That capability is Hard-gated: the consequence if wrong is double-spend or unrecoverable loss, so it never runs on the agent's own authority.

    The Agent Owner is Responsible: they draft the plan amendment naming the payment tool, the scope, and the cost ceiling. The Finance Owner is Consulted on the ceiling and the evidence required — a recorded human approval plus an invoice reference. The Approver is Accountable and is not the Agent Owner: they approve or reject, and the decision writes an audit row with their identity on it. The Incident Lead is Informed, because a money-moving capability changes what an incident can cost. Later, each payment still routes as its own hard-gated action; the RACI approved the *capability*, and the gate approves each *use*. If no approver answers, the payment fails closed, and the block surfaces to the owner with the exact evidence that would unblock it.

    Common failures¶

    • Two Accountables. Owner and approver both "sign off," so neither can be asked, alone, why the decision was made.
    • The approver is the requester. Self-approved grants and ceiling raises are the privilege-escalation path, formalised.
    • Consulted becomes a silent veto. A Consulted role that never answers must escalate on a timeout the policy names — otherwise consultation is a pocket block with no audit row.
    • Informed means an unread alias. If the Informed name is a mailbox nobody opens, incident notice goes nowhere. Name a human, and test the route.
    • The chart lives outside the gates. A RACI the approval routing never reads decays the first time someone changes role.

    Wire the RACI into the gates, or it is just a document¶

    The chart earns its keep when the machinery reads it. Approval routing should resolve the Accountable name from the row, not from whoever is online. The escalation timeout and plan expiry are policy values you fill in — [TIMEOUT], [DURATION] — and when either lapses with no decision, the default is fail-closed: the action blocks, the block is recorded, and it surfaces to the Accountable name in plain language. When a person changes role, update the chart and the routing together, in the same operation, and record the change as an audit row — policy text is evidence too.

    The starter version¶

    Do not chart every agent today. Take the agent with the highest-consequence capability — the one that can move money, send externally, or read credentials — and fill in all twelve rows for it in one sitting, with real names. Route one hard-gated approval and one block through those names, and confirm both land where the chart says. That single completed AI agent governance RACI template beats a fleet-wide chart of team aliases: every decision for that agent now has one human who does it, one who decides it, and a record that proves both.

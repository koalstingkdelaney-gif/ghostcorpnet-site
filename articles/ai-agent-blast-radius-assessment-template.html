AI Agent Blast Radius Assessment Template: Map What an Agent Can Reach Before It Goes Wrong

    Most teams assess an agent by its intent: what it is supposed to do. Production asks a harder question: what can this agent reach if it goes wrong \u2014 if it misreads an instruction, loops, follows text it should have treated as data, or its credentials are misused? That total reach is its blast radius: the tools it can call, the data it can read or change, the money it can spend, the places it can send data, the other agents it can invoke, and the time it can keep doing it before anyone notices. This AI agent blast radius assessment template, taken from the Governed Agent Mesh Playbook, maps that reach agent by agent, before deployment, so you can shrink it on paper instead of after an incident.

    Intent is not a boundary¶

    A prompt describes what an agent should do. It does not limit what the agent can do. The limit is set by the machinery around the agent: its identity, its grants, its tools, its ceilings, and its expiry. The Playbook's core rule is that no action happens without an attributable, owner-scoped identity and an explicit grant \u2014 anonymous or shared actors are rejected, not warned about. A blast radius assessment starts there, because an agent with a vague identity and ambient permissions has a radius nobody has actually measured, however careful its instructions sound.

    A permission list alone does not measure it¶

    A list of permissions looks like a measurement and is not one, for three reasons. First, it is written per tool, while harm travels across tools: read access plus egress plus a long-running plan is a different risk than any one alone. Second, it rarely records time \u2014 a grant lasting an hour and the same grant lasting a quarter describe very different incidents. Third, it almost never records delegation: an agent that can invoke another agent inherits a path into that agent's reach. The assessment below forces those three into the open.

    The six reach dimensions to map¶

    Write one line per dimension, per agent. A dimension you cannot describe is a dimension you have not bounded.

    • Tools and side effects \u2014 every tool the agent may call, and the worst side effect each can produce: a changed record, a sent message, a deleted file, a changed permission. Name the irreversible ones explicitly; reversibility is what separates an error from an incident.
    • Data classes \u2014 the most sensitive class the agent can read, and the most sensitive it can write or move. The Playbook bounds every plan by data class; the radius is set by the highest class reachable, not the one used on a normal day.
    • Money and spend ceiling \u2014 the most the agent can spend or commit before a hard stop. Ceilings belong on the plan, not the account, and when one is hit the result is blocked and recorded \u2014 not retried, not warned, not billed. The documented stakes: a developer reported an agent in an infinite loop burning over $700 in API credits in 72 hours because nothing in the stack had budget controls or a watchdog.
    • Egress destinations \u2014 every place data can leave: domains, storage, other systems, other people. Default-deny is the only honest starting point; each allowed destination is a named line, not an assumption.
    • Delegation and invoked agents \u2014 every agent, sub-agent, or workflow this agent can start, with their radii attached. A child agent must never receive a wider grant than its parent was assessed for, and the chain must expire with the parent.
    • Time and persistence \u2014 how long grants live, how long a run may continue, what state survives between runs, and how quickly a human would see a problem in the audit trail. Time multiplies every other dimension.

    The AI agent blast radius assessment template: fields to copy¶

    One assessment per agent, reviewed before the first production run. Replace every [BRACKET]:

    • Agent identity \u2014 the stable, owner-scoped identity, and the named human owner: [IDENTITY / OWNER].
    • Plan and workload \u2014 the approved work this assessment covers, in one sentence: [PLAN]. Work outside it is outside the assessment.
    • Tools and worst side effects \u2014 [TOOL \u2014 worst effect \u2014 reversible? yes/no] per tool.
    • Data classes reachable \u2014 read: [CLASS]; write/move: [CLASS].
    • Spend ceiling and other cost bounds \u2014 [CEILING per plan / per day], failing closed at the limit.
    • Egress allowlist \u2014 [DESTINATION and data class allowed to it] per line; everything else denied.
    • Delegation map \u2014 [AGENT invoked \u2014 grant it receives \u2014 its expiry]; write NONE if the agent invokes nothing.
    • Time bounds \u2014 grant expiry: [EXPIRY]; maximum run length: [LIMIT]; state retained between runs: [STATE or NONE].
    • Risk tier per capability \u2014 hard-gated, bounded auto, or draft-only, following the Playbook tiers: money, contracts, external outreach, credentials, and permission changes are always hard-gated human decisions.
    • Detection \u2014 the audit rows and review cadence that would show this agent exceeding its assessed reach: [REVIEW].

    Score it, then shrink it¶

    Do not average the dimensions into a comforting score. The radius is set by the worst reachable combination: sensitive data plus open egress, or a spending tool plus a long expiry, is the finding, even if every other line is tight. Work through the shrink levers in order:

    • Remove tools the plan has not proven it needs; a tool that is absent cannot be misused.
    • Narrow the data class to the specific records the workload uses, not the store they live in.
    • Lower the ceiling to what one plan legitimately costs, and let it fail closed.
    • Shorten expiry to the task: a grant matched to the work, not to the calendar quarter.
    • Cut or bound delegation \u2014 child grants narrower than the parent's, expiring with it, each hop audited.
    • Split one wide agent into two bounded agents whose radii do not overlap, so no single compromise reaches both.
    • Hard-gate the irreversible actions so a bad run stops at a human decision instead of completing.

    Two short walkthroughs¶

    A support agent. Assessed reach: read internal help content and public tickets, draft replies, no refund or account tools at all, egress only back into the ticketing system, delegation NONE, grants expiring with the shift-length plan. Its worst day is a wrong draft a human still has to send \u2014 because sending is hard-gated \u2014 not a changed account.

    A research agent. Assessed reach: read internal reports, call a metered search tool under a per-plan ceiling, write only to one named workspace, egress to that workspace only, no delegation, short expiry. Its worst day is a wasted ceiling, blocked and recorded at the limit \u2014 not data leaving to an unlisted destination, because unlisted destinations are denied.

    In both cases the assessment makes the worst day small.

    When the assessment expires¶

    A blast radius is a property of a configuration, so it expires when the configuration changes. Re-run the assessment whenever a tool is added, a data class widens, a ceiling or expiry is raised, a new delegation appears, or the model changes \u2014 a model swap can change behaviour inside identical permissions. Record the new assessment as a new version; never edit the old one silently.

    The audit trail is the proof the radius held¶

    The Playbook's audit row records actor, action, target, outcome, and timestamp, hash-chained to the previous row so tampering breaks the chain visibly. The assessment gives those rows something to be checked against: compare what the agent actually reached with what the assessment said it could reach. Any reach outside the assessed lines is either a block that fired correctly or a finding. When evidence is missing, the system blocks and records; it never degrades to a warning.

    Common mistakes to avoid¶

    • Assessing the happy path \u2014 mapping what the agent normally touches instead of everything it can reach.
    • Just-in-case grants \u2014 permissions added for a hypothetical task widen the radius for every real one.
    • Forgetting delegation \u2014 the radius quietly doubles through an invoked agent nobody assessed.
    • No time dimension \u2014 the same reach for a month is not the same risk as for an hour.
    • Averaging away the worst line \u2014 one open dimension is the incident; the tidy others do not compensate.

    Pre-launch checklist¶

    • Every agent has a completed assessment: identity, owner, plan, tools, data classes, ceiling, egress, delegation, and time bounds all named.
    • Irreversible and hard-gated capabilities \u2014 money, contracts, outreach, credentials, permission changes \u2014 require a human decision in every case.
    • Spend ceilings fail closed, grants expire with the task, and child grants never widen beyond the parent.
    • Audit rows are hash-chained and reviewed against the assessment; re-assessment triggers are written down and owned.

    Conclusion¶

    An AI agent blast radius assessment template turns a vague worry \u2014 what if it goes wrong? \u2014 into six mapped dimensions, shrink levers, and an audit check. Map the reach before the first run, and re-map it every time the configuration changes.

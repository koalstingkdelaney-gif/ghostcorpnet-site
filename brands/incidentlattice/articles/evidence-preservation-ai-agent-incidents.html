Evidence preservation for AI agent incidents: logs, prompts, and tool calls

Published 2026-11-05T00:00:00-05:00 ·

The Imperative of Evidence Preservation

When an AI agent malfunctions—whether it hallucinates sensitive data, executes unauthorized actions, or enters an infinite loop—the incident response timeline is dictated by the volatility of the system's state. Unlike traditional software, where logs are often static, AI agent state is ephemeral. Context windows, transient memory, and temporary tool execution environments are frequently overwritten or purged within minutes of an incident.

For on-call engineers, the first hour of an incident is not just for remediation; it is for forensic preservation. If you wait until the issue is "fixed," you may find that the exact prompt chain, the specific model version, and the sequence of tool outputs that triggered the behavior have been rotated out of cache or overwritten by subsequent agent turns.

Data to Capture in the First Hour

To perform an accurate root cause analysis (RCA), you must capture the full "thought process" of the agent. Do not rely on high-level application logs alone. You need the raw data exchanged between the application layer, the orchestration framework, and the LLM provider.

1. The Prompt Chain and Context

Capture the exact input provided to the model, including system instructions, few-shot examples, and the user’s input. If the agent uses Retrieval-Augmented Generation (RAG), you must capture the specific retrieved chunks provided to the model at that exact timestamp. Without the retrieved context, you cannot determine if the agent hallucinated or if it was fed incorrect data.

2. Tool Calls and Execution Artifacts

AI agents often interact with APIs or databases. Capture the full tool call payload: the arguments passed to the tool, the raw response returned by the tool, and any error codes generated during the execution. If the agent performed a multi-step workflow, document the sequence of calls. A common failure point is an agent misinterpreting a tool's output; you cannot debug this without seeing the raw JSON response the agent received.

3. Model and Configuration Metadata

The behavior of an agent is highly sensitive to its configuration. Record the following:

  • Model ID: Include the specific version or snapshot ID (e.g., gpt-4o-2024-05-13). Do not assume the "latest" version is in use.
  • Hyperparameters: Capture the temperature, top-p, and presence penalty settings used during the incident.
  • System Prompt Version: If you use prompt templating, record the exact version or hash of the prompt template used.

4. Approvals and Human-in-the-Loop (HITL) State

If the agent requires human approval for specific actions, capture the state of that approval request. Did the agent pause? Was the approval bypassed? Capture the identity of the human approver and the timestamp of the action.

Retention and Access Control

Evidence gathered during an incident is sensitive and potentially contains PII or proprietary trade secrets. Establish a "Cold Storage" protocol immediately upon incident declaration.

  • Immutable Storage: Move captured logs to an immutable bucket or a read-only forensic repository. Ensure that the incident response team has write-once, read-many (WORM) access to prevent accidental deletion during the heat of the incident.
  • Access Logging: Log every instance of an engineer accessing these forensic artifacts. Because this data may contain user data, access must be strictly limited to those involved in the incident response and the subsequent RCA.
  • Encryption: Ensure the forensic storage is encrypted at rest and in transit, specifically if the logs contain sensitive user inputs or internal system instructions.

Chain-of-Custody Habits

Digital evidence is only valuable if its integrity can be verified. Adopt these habits to ensure your evidence holds up during the post-mortem phase:

  • Hashing: Generate SHA-256 hashes for all log files and data exports immediately upon capture. Store these hashes in your incident ticket.
  • Time Synchronization: Ensure your log timestamps are normalized to UTC. AI agents often span multiple microservices; if timestamps are skewed, reconstructing the causal chain becomes impossible.
  • Snapshotting: If the agent runs in a containerized or virtualized environment, take a snapshot of the environment state if possible. This allows you to inspect environment variables and local file system changes that might have influenced agent behavior.

What Not to Alter During Containment

The urge to "fix forward" can destroy forensic evidence. To preserve the state for investigation, follow these constraints:

  • Avoid Clearing Caches: Do not purge Redis, Memcached, or other transient data stores that the agent uses for memory or state management until the data has been exported.
  • Do Not Reset Model Configs: If you suspect a configuration error, document the current state before updating it. Do not overwrite the existing config file; create a new one.
  • Avoid Redeploying: If possible, isolate the affected agent instance (e.g., remove it from the load balancer) rather than redeploying the service. A redeploy may wipe the container logs or volatile memory that contains the "smoking gun."

Self-Check List: Forensic Readiness

Use this checklist during the first hour of an incident to ensure you haven't missed critical data:

  • [ ] Have I captured the raw model input, including system prompt and RAG context?
  • [ ] Did I export the full history of tool calls and tool responses?
  • [ ] Have I recorded the specific model version and temperature settings?
  • [ ] Is the evidence stored in an immutable, read-only location?
  • [ ] Have I generated and recorded hashes for all collected log files?
  • [ ] Did I isolate the affected instance rather than performing a destructive redeployment?
  • [ ] Have I documented the identities of all personnel who accessed the forensic data?
